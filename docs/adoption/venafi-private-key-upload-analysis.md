# Pushing cert-manager Private Keys to Venafi TPP

Status: Analysis
Scope: Venafi TPP issuer
Purpose: Determine whether cert-manager can push a generated private key to TPP so another cert-manager instance can reuse the certificate.

## 1. Temporary key versus final key

The temporary private key generated by cert-manager is the same key material that ends up in the final Secret.

Flow:

```text
keymanager
  -> generates or reuses the private key
  -> writes it to the temporary Secret as PKCS#8

requestmanager
  -> reads the temporary key
  -> builds the CSR from it

Venafi issuer
  -> sends the CSR to TPP
  -> TPP issues a certificate for that public key

issuing controller
  -> reads the same temporary key
  -> verifies the CSR public key matches the key
  -> verifies the issued certificate public key matches the CSR
  -> writes tls.crt, tls.key, ca.crt to the final Secret
  -> the temporary Secret is deleted
```

Relevant code:

- `pkg/controller/certificates/keymanager/keymanager_controller.go:349-370`
  - `createNewPrivateKeySecret` always encodes the temporary key as PKCS#8.
- `pkg/controller/certificates/requestmanager/requestmanager_controller.go:359-405`
  - requestmanager decodes the temporary key and builds the CSR.
- `pkg/controller/certificaterequests/venafi/venafi.go:123,151`
  - the Venafi issuer sends the CSR and retrieves the certificate.
- `pkg/controller/certificates/issuing/issuing_controller.go:195-367, 418-432`
  - the issuing controller reads the temporary key, validates it, and writes the final Secret.

Important details:

- The key material is identical.
- The encoding can differ:
  - temporary Secret: always PKCS#8;
  - final Secret: re-encoded using `spec.privateKey.encoding` (default PKCS#1).
- With `spec.privateKey.rotationPolicy: Always`, the temporary key is a new key for that issuance.
- With `spec.privateKey.rotationPolicy: Never`, the temporary key is a copy of the key already stored in `spec.secretName`.
- The temporary Secret is deleted after issuance.
- TPP never sees the private key; it only sees the CSR.

## 2. Can the private key be pushed to TPP?

Out of the box: no.

cert-manager sets `CsrOrigin = certificate.UserProvidedCSR` in
`pkg/issuer/venafi/client/request.go:153` and sends only the PKCS#10 CSR. It never sends `tls.key` to TPP.

Technically: yes, through the TPP `Certificates/Import` API.

TPP supports importing a certificate with its private key:

```http
POST /vedsdk/Certificates/Import
{
  "PolicyDN": "\\VED\\Policy\\TeamA",
  "ObjectName": "app.example.com",
  "CertificateData": "-----BEGIN CERTIFICATE-----...",
  "PrivateKeyData": "-----BEGIN PRIVATE KEY-----...",
  "Password": "<protects PrivateKeyData>",
  "Reconcile": true
}
```

TPP import requirements:

- Token scope: `Certificate:Discover`.
- Permissions: Master Admin, or View + Read + Write + Create + Private Key Write on the certificate object.
- `PrivateKeyData` requires `Password`.
- The private key can be RSA or PKCS#8 PEM.
- The response includes `PrivateKeyVaultId` when the key is stored.

vcert support:

- `tpp.Connector.ImportCertificate` at
  `/Users/samtyga/go/pkg/mod/github.com/!venafi/vcert/v5@v5.12.2/pkg/venafi/tpp/connector.go:1693`
- `certificate.ImportRequest` at
  `/Users/samtyga/go/pkg/mod/github.com/!venafi/vcert/v5@v5.12.2/pkg/certificate/certificate.go:174`
- Fields: `PolicyDN`, `ObjectName`, `CertificateData`, `PrivateKeyData`, `Password`, `Reconcile`, `CustomFields`.

`Reconcile` semantics from the TPP documentation:

- `false` (default): import and replace. Import the certificate into the policy folder regardless of whether a past, future, or same version exists.
- `true`: import but use newest. Only import when no certificate object exists with a past, present, or current version. If a match is found, activate the certificate with the most current `Valid From` date and archive the unused certificate.

cert-manager currently requests only `certificate:manage`
(`pkg/issuer/venafi/client/venaficlient.go:50`). Importing a key therefore requires a token scope change or a separate TPP identity.

## 3. Option A - push the key inside the Venafi issuer `Sign()`

Insertion point: after `RetrieveCertificate` returns the issued certificate and before returning the `IssueResponse`.

At that moment:

- TPP has issued the certificate.
- The temporary private-key Secret still exists.
- `cr.Annotations[cmapi.CertificateRequestPrivateKeyAnnotationKey]` names the temporary Secret.
- `v.secretsLister` can read `tls.key`.

Proposed flow:

1. Parse the issued certificate and keep the leaf certificate.
2. Read the temporary Secret named by `cert-manager.io/private-key-secret-name`.
3. Read `tls.key` (PKCS#8).
4. Generate an ephemeral strong password.
5. Call TPP `Certificates/Import` with:
   - `CertificateData`: the leaf certificate,
   - `PrivateKeyData`: the temporary `tls.key`,
   - `Password`: the ephemeral password,
   - `PolicyDN`: the issuer zone,
   - `ObjectName`: the same friendly name used by `RequestCertificate`,
   - `Reconcile`: chosen after lab validation.
6. Record the imported DN, GUID, and thumbprint on the CertificateRequest or Certificate.
7. Return the certificate as usual.

Required changes:

- Add `ImportCertificate` to `venaficlient.Interface`.
- Implement it using `tpp.Connector.ImportCertificate`.
- Extend the internal `connector` interface, the instrumented wrapper, and the test fakes.
- Change `tppScopes` to include `certificate:discover`.
- Read the temporary Secret in the issuer.
- Add tests for:
  - import success,
  - import failure,
  - missing temporary key,
  - missing token scope or permission,
  - repeated `Sign` calls and idempotency.

Advantages:

- Fewer new files than a separate controller.
- The key and certificate are available at the same point in the flow.
- No new controller registration.

Disadvantages:

- Couples certificate issuance to key upload.
- If the import fails, either issuance is blocked or the key is never uploaded and there is no retry after the CR is marked Issued.
- Changes the main issuer token scope globally for every Venafi TPP user.
- The issuer controller reads private key material directly.
- The temporary Secret is the source, so timing matters.

## 4. Option B - separate key-upload controller

A new controller watches Certificates and Secrets, and after the final Secret is written, uploads the certificate and private key to TPP.

Proposed flow:

1. Watch Certificates and the Secret named by `spec.secretName`.
2. Act only when:
   - the Certificate opts in, for example with
     `venafi.cert-manager.io/upload-private-key: "true"`;
   - the issuer is Venafi TPP;
   - the Secret contains `tls.crt` and `tls.key`.
3. Decode the certificate and private key.
4. Check the certificate public key matches the private key.
5. Record the certificate thumbprint.
6. Skip if the same thumbprint was already imported.
7. Call TPP `Certificates/Import`.
8. Record the imported DN, GUID, and thumbprint in a Secret annotation or Certificate condition.
9. Retry on failure without affecting the Certificate's readiness.

Required changes:

- Reuse the new `ImportCertificate` client method.
- New controller with Certificate and Secret listers and a Venafi client builder.
- Opt-in annotation.
- Idempotency using the certificate thumbprint.
- Tests and controller registration.
- A dedicated TPP credentials Secret/token with `certificate:discover` and Private Key Write, if you want to avoid changing the main issuer scope.

Advantages:

- Certificate issuance is independent of key upload.
- Upload retries independently.
- Can use a dedicated TPP identity and policy folder.
- Reads the stable final Secret, not the temporary Secret.
- Easier to opt in per Certificate.
- Lower operational risk.

Disadvantages:

- More code: controller, listers, tests, registration.
- More configuration if a separate token/credentials Secret is used.
- Needs idempotency and renewal handling.

## 5. Comparison

| Aspect | In-place in `Sign()` | Separate key-upload controller |
|---|---|---|
| New code | Small | Larger |
| Coupling to issuance | High | None |
| Retry on import failure | Only while the CR is not Issued | Independent retry |
| Token scope | Main issuer scope must include `certificate:discover` | Can use a dedicated token/Secret |
| Private key access | Issuer controller reads the temporary key | Isolated controller reads the final Secret |
| Timing | Before the temporary Secret is deleted | After the final Secret is written |
| Idempotency | Needs a CR annotation | Thumbprint comparison |
| Renewal | Re-import on each `Sign` | Re-import when the thumbprint changes |
| Operational risk | Higher | Lower |

## 6. Critical caveats

### 6.1 `Reconcile` and duplicate objects

Before choosing either option, test TPP `Certificates/Import` in a lab:

- Does `Reconcile: true` attach the private key to the existing CSR-created object?
- Does `Reconcile: false` replace the existing object?
- Does either option create a second certificate object?

If TPP creates a second object, the adoption search must prefer the candidate that actually has a private key. Otherwise another cert-manager may find the keyless CSR-created object first and skip adoption.

### 6.2 Token scope and permissions

- The import requires `Certificate:Discover`.
- The identity needs Private Key Write on the certificate object or policy folder.
- The current cert-manager TPP identity uses `certificate:manage` only.
- A separate token/identity for key upload is safer.

### 6.3 Security

- TPP will store private keys generated inside Kubernetes.
- This changes the trust boundary and may violate TPP policy.
- Use a dedicated identity restricted to the required policy folder.
- Never log the private key or the import password.
- Use an ephemeral strong password for each import.
- Confirm with the TPP administrator that private key import is allowed.

### 6.4 Timing and idempotency

- In the issuer path, the temporary Secret exists only until issuance completes.
- A failed import after the CSR is Issued cannot be retried by the issuer without additional state.
- A separate controller can retry from the final Secret safely.
- Record the imported certificate thumbprint to avoid repeated imports.

### 6.5 Renewal

- Each renewal can produce a new key depending on `rotationPolicy`.
- The upload step must run again for the new certificate/key pair.
- The thumbprint comparison distinguishes a new certificate from an already-imported one.

## 7. Recommendation

Implement the `ImportCertificate` client method once, then use a separate key-upload controller.

Reasons:

- It keeps issuance independent from TPP import failures.
- It can retry safely from the final Secret.
- It can use a dedicated TPP identity with `certificate:discover` and Private Key Write.
- It is opt-in per Certificate.
- It avoids changing the main issuer token scope for all users.

A separate controller is more code than changing `Sign()`, but the in-place option couples certificate issuance to a security-sensitive side effect and changes the global token scope. For a long-lived feature, the separate controller is the safer design.

Before implementing, validate TPP `Certificates/Import` behavior in a lab, especially whether `Reconcile` merges the key into the existing certificate object or creates a duplicate object.
